## 議題

カット表・再現プロンプト生成ツールを、これからどう育てるべきか。

現状:

- 参照動画をドロップすると、カット分割 → キーフレーム抽出 → Claude による解析 →
  カット表(Markdown / CSV / HTML)と 2 種類のプロンプトが出るところまで動いている
- 被写体を抜いた汎用プロンプトを作り、別の被写体に差し替えられる
- Mac アプリ化と、iPhone から iCloud 経由で投げる自動処理まで実装済み
- 利用者は開発者本人ひとり。制作作業の効率化が目的で、外販は今のところ考えていない

問うべきこと:

- 次に作るべき機能は何か。そもそも機能を足すべきなのか
- この道具が本当に解いている問題は何か。解けていない問題はどれか
- いま見落としている、より大きな機会はあるか

## 結論(議長)

# 議長まとめ

## 1. 結論

このツールはコア機能(カット検出・解析・プロンプト生成)が早期に完成した後、Macアプリ化・iPhone連携・council自動化という「作るための仕組み」にばかり投資が向き、肝心の「生成したプロンプトが本当に狙った映像を作れているか」を一度も検証していない。全評価者がこの一点(表現は違えど)に収束した。今回の合議で決めるのは新機能ではなく、この検証を今週の唯一の作業とすることだ。反対役が指摘した「council構造に停止条件がない」という点は事実として認め、仕組み自体に反映する。「開発が自己目的化しているか」という大きな判定と、前提破壊役が投げた「技術的恒常性が崩れるのでは」という土台への疑問は、検証データが無い今は判断材料が無く保留する。

## 2. 判断

**採用**

1. **実行役の案D(3カットを実際の生成AIに投げる)+拡張役の案1(生成結果を同じパイプラインで再解析し構造的にdiffを取る)の合体案。** 相互評価で評価者4・5が独立に同じ組み合わせに辿り着いており、収束度が最も高い。しかも新規インフラ不要で今日から着手できる。
2. **反対役の「実績データが存在しない」という指摘。** 処理本数・被写体差し替え回数・iPhone連携使用回数はゼロコストで数えられる客観的事実で、反証可能。検証タスクのついでに取得する。
3. **反対役の「council の役割設計に "作らなくていい" という選択肢が最初から無い」という指摘。** 役割定義を読めば真偽が判定できる具体的な主張で、評価者4・5双方が最も鋭いと支持した。仕組みを直す。

**却下**

1. **前提破壊役②「本人ひとりというのは建前で、実は他人に見せたい」という反転。** 評価者4の指摘通り根拠のない人格推測で検証不能。
2. **拡張役の案4(council を生成物の品質チェックに転用)。** メタ機能をさらに拡張する提案であり、反対役の中心的批判(仕組みづくりへの自己目的化)にそのまま当てはまる。今はやらない。
3. **拡張役の案2・3(ジャンル傾向集計、cuts.json尺での自動結合)。** アイデアとしては筋が通るが、「プロンプトが狙った映像を作れているか」が未検証なまま応用を広げるのは順序が逆。案D+A1の結果が出るまで着手しない。

## 3. 次の行動

1. **3カットを実際の生成AI(Veo)に投げ、参照サムネイルと並べる。** 完了基準: 生成動画3本と参照カットのサムネイルを並べたファイルができている。所要: 半日。
2. **生成された3本を `extract_cuts.py` → cutsheet解析にもう一度通し、参照側 cutsheet.json と手動でdiffする(カメラワーク・ショットサイズ・尺)。** 完了基準: 3カットそれぞれについて「一致」または「不一致(どのフィールドがどうずれたか)」が記録されている。所要: 半日(1と合わせて1日)。
3. **これまでの処理本数・`apply_subject.py` の使用回数・iPhone連携の使用回数を数える。** 完了基準: 3つの数字が記録されている。所要: 30分。
4. **体系的なズレ(3カット中2つ以上で同種の不一致)が出た場合のみ、`build_cutsheet.py` / `apply_subject.py` のプロンプトテンプレートを修正。出なければ何もしない。** 完了基準: 修正後に同じ3カットで再生成しズレ解消を確認、または「修正不要」と記録して終了。所要: 半日(発生時のみ)。
5. **`council/roles/` の実行役・議長のプロンプトに「今週やることがない、という結論を出してよい」旨を明記する。** 完了基準: role定義ファイルに追記され、次回council実行時に「停止」が選択可能な結論として機能する。所要: 15分。

## 4. 保留

- **前提破壊役⑤(技術的恒常性の崩壊)。** 生成AIが参照動画を丸ごと渡すだけでスタイル模倣できるなら、分解パイプライン自体が回り道になる。行動1のついでに「参照動画そのものをそのまま生成AIに渡す」パターンも1回だけ試し(評価者5の指摘通りコストほぼゼロ)、分解パイプラインの結果と比べておく。ここで分解パイプラインが明確に劣っていれば次回議題に格上げする。
- **「開発が自己目的化しているか」という反対役の中心的主張。** 行動3で処理本数などの実績データが揃うまで、この主張の是非は判定できない。次回council開催時には数字が出ているはずなので、その時点で再判定する。

### 反対役

# 反対役

## 最も強い反対論

このツールは「動画制作を効率化する」という当初の目的から、**「ツールを作るためのツールを作る」自己目的化のループ**に入りつつある。

直近のコミット履歴を見ると、コア機能(カット検出・解析・プロンプト生成)はかなり早い段階でほぼ完成している。それ以降に積まれているのは Mac アプリ化、AppleScript droplet、iCloud 経由の自動処理、そして今回の 5 役合議制の自動実行——すべて「制作物」ではなく「制作するための仕組み」への投資だ。

決定的なのは合議システムの構造そのものだ。5 役のうち「実行役」は"次に何をすべきかだけを考える"役と定義されており、「これ以上何も作らなくていい」という選択肢が最初から役割設計に存在しない。議長も「具体的な次の行動を決める」ことが仕事であり、「行動しない」という結論を出す動機がシステムのどこにもない。5 時間ごとに自動で回り続けるこの仕組みは、放っておいても機械的に「次の機能」を提案し続ける構造になっている。今この文章が書かれていること自体が、その構造が意図通り動いていることの証拠でしかない。

そして肝心の「動画を何本作ったか」「その効率化でどれだけ時間が浮いたか」は、README にも設計書にも一切記載がない。開発工数(コミット数・機能の複雑さ)だけが可視化されていて、目的だったはずの成果物(動画制作の実績)が見えない。これは目的と手段が入れ替わっている典型的な兆候であり、次に機能を足すべきかを合議で決める前に、そもそも「このツールは何本の動画制作に使われたのか」を自問すべきだ。

## その他の反対論

**実績データの不在**
「制作作業の効率化が目的」と言いながら、実際にこのツールを使って何本の参考動画を分析し、何本の動画を作ったのかという実績が一つも語られていない。開発ログ(コミット)は詳細に残っているのに、利用ログがない。これでは「効率化できている」という主張自体が検証不能で、次の機能追加の是非を判断する材料がそもそも存在しない。

**人力との比較が一度もされていない**
参照動画1本を目視でメモしてカット表を作る場合、実際どれくらいの時間がかかるのか測られていない。一方このツールは、セットアップ・カット検出・キーフレーム抽出・Claude 解析の待ち時間・トラブル対応(Terminal 権限、iCloud 同期)を含む。特に iPhone → iCloud → 1分ごとのポーリング監視という経路は、"その場で確認したい"というニーズに対して非同期の待ち時間を新たに挟んでいる。人力なら見た瞬間に終わっていた作業を、わざわざ遅くしている可能性を検証していない。

**「無料」という前提の脆さと維持コストの累積**
「API従量課金が発生しない」という経済性は、Claude Code の定額プランの範囲に収まっている間だけ成立する。しかし README 自身が「利用枠が5時間単位で切り替わる」ことを合議システムの設計根拠にしており、カット表生成もこの同じ枠を食い合う。量産(被写体差し替えで複数本作る)に進めば、この前提はまず崩れる。加えて Mac アプリ・droplet・watcher・council と保守対象が増えるほど、OS や CLI の仕様変更で壊れる箇所が増え、その復旧に費やす時間が本来の「動画制作」から奪われ続ける。

## 反対が外れる条件

- このツールで実際に処理した参照動画の本数と、それぞれで人力比較した所要時間(セットアップ・待ち時間・トラブル対応込み)のログが示され、明確に人力より速いと確認できること。
- 合議システムが少なくとも一度、「これ以上機能を足す必要はない」という結論を実際に出した記録があり、常に"何か作る"方向にしか倒れない構造ではないと確認できること。
- 量産用途(被写体差し替えを使った複数本生成)を試した際に、定額プランの利用枠を圧迫せずに回せることが実測で確認できること。

### 前提破壊役

# 前提破壊役としての応答

## 1. 発見した暗黙の前提

1. **目的の自明性**: 「カット表(構造化データ+Markdown/CSV/HTML)を出力すること」自体が目的達成に必要だ、と当然視されている。
2. **利用者像**: 「開発者本人ひとりが使う」という建前と、実際の実装投資(Macアプリ化、ドラッグ&ドロップ、iPhone/iCloud連携、5役合議の自動実行)が一致していないのに、誰も指摘していない。
3. **手段の固定**: 「動画をカット単位に分解し、言語化して解析する」ことが、参照動画のスタイルを再現する最善の経路だと固定されている。
4. **成果物と人間介在**: 表とプロンプトを出力し、人間がコピー&ペーストして別の生成AIに貼る、という手順が最終形だと思われている。
5. **技術の恒常性**: このツールが埋めている「動画→構造化解析→プロンプト」というギャップは、来年も埋まったままだという前提で設計・投資判断がされている。

## 2. 各前提の反転

**① 目的の自明性を反転**
もし「カット表」というアウトプット自体が不要で、本当に欲しいのが「同じ雰囲気の動画」そのものだったら？ 中間成果物としての表・JSON・プロンプトは全部使い捨てのログでよく、UIも要らない。今後注力すべきは「表の見やすさ」ではなく「動画→動画」を直結するパイプラインになる。カット表は目的ではなく、目的を達成できなかった時代の代替物だったと分かる。

**② 利用者像を反転**
「本人ひとり」が嘘で、実際には「他人に見せたい/使われたい」が動機だとしたら？ Macアプリ化やiPhone連携、5役合議の演出性(役割分担・議事録・自動実行)は、実用効率よりも「見せられるプロダクト」を作る行為に見える。この場合、次にやるべきは機能追加ではなく、誰に見せたいのか・なぜ隠しているのかを言語化することになる。外販を「今のところ考えていない」という一文自体が、考えていることの裏返しかもしれない。

**③ 手段の固定を反転**
「分解しない」方が精度が高い世界だったら？ 生成AI側(Veo/Sora/Klingなど)がすでに参照動画を丸ごと渡してスタイル模倣できる、あるいは近く出来るようになるなら、カット分割・キーフレーム抽出・構造化スキーマという丹念な設計(README/DESIGN.mdの核)は、精度でも工数でも劣る回り道になる。この場合、次の一手は「機能追加」ではなく「分解パイプラインを迂回する実験」であるべきになる。

**④ 成果物と人間介在を反転**
コピー&ペーストという人間の手作業が、実は最大のボトルネックだったら？ カット表を経由せず「動画を投げたら動画が返る」自動化(生成AIのAPIと直結、MCP的な連携)がすでに技術的に可能なのに、あえて人間の目視・コピペ・被写体入力という工程を残している。もしこれが「無意識に自分の仕事を残すための設計」だったとすれば、効率化ツールという触れ込みと矛盾する。

**⑤ 技術の恒常性を反転**
生成AIが来年、動画理解と動画生成を統合し、「この動画の雰囲気で、被写体はXで」と直接指示するだけで済むようになったら？ カット検出・キーフレーム抽出・構造化解析・2種のプロンプト生成という現在の設計は、まるごと「AIが自分でやる中間工程」に飲み込まれる。このツールの価値は「解析結果」ではなく「人間がレビュー・修正できる中間表現を残すこと」に縮小し、それすら不要になれば存在意義自体が消える。

## 3. 最も危険な前提

**最も危険なのは⑤「技術の恒常性」。**

理由: これは他の4つの前提すべての土台になっている。①〜④が個別に崩れても部分的な手戻りで済むが、⑤が崩れると「分解して構造化し、2種のプロンプトを人間がコピペする」という設計思想全体(README・DESIGN.mdの中核、Mac化・iPhone連携という配布インフラ、さらには5役合議という開発方針決定インフラそのもの)が、土台から意味を失う。

しかも今回、開発者は「次に何を作るべきか」を5時間ごとに自動でAIに議論させる仕組み(council)まで作った。これは「今の設計思想は当面正しい」という前提の上に、さらに"その前提の上で次の一手を決め続ける"仕組みを重ねている。もし土台(⑤)が崩れていたら、この合議制自体が、消えゆく設計の周辺を最適化し続ける空回りの装置になる。被害が大きいのは、機能単体の無駄ではなく、「間違った土台の上に意思決定プロセスそのものを自動化してしまった」ことによる継続的な労力の垂れ流しだからだ。

### 拡張役

# 見落としている可能性

**1. 生成結果を同じパイプラインで再解析し、参照との差分を取る(フィードバックループ化)**
いまツールは「参照動画 → プロンプト」で止まっている。プロンプトを Veo/Sora/Kling に貼った後、出来た動画が参照とどれだけ似ているかは目視でしか判断していないはず。生成された動画を `extract_cuts.py` → Claude解析 に**もう一度**通し、できあがった cutsheet.json 同士を突き合わせれば、「カメラワークが違う」「尺がずれた」を数値・構造で検出できる。`build_cutsheet.py` にはすでに被写体漏れを検証するロジックがあるので、同種の diff ロジックを足すだけで済む。→ **生成AIの当たり外れを勘ではなく構造化データで判定でき、プロンプトの自動修正案まで出せるようになる。**

**2. 複数本のカット表を蓄積して、ジャンル単位の傾向を見る**
被写体レイヤとスタイルレイヤを分離したスキーマは、1本ずつ使い捨てるにはもったいない設計になっている。同じジャンルの参照動画を10〜50本通して cutsheet.json を溜めれば、「このジャンルではCUとドリーインが何割か」「照明はどのパターンが多いか」を集計できる。→ **撮る前に、狙っているジャンルの「型」を定量的に把握できるようになる。**

**3. カットごとの生成クリップを cuts.json の尺で自動結合する**
`cuts.json` には各カットの正確な尺とタイムコードがすでにある。カットごとに生成した動画クリップをそこに当てはめて ffmpeg concat すれば、プロンプトを作って終わりではなく「参照動画と同じ尺配分の通し動画」まで自動で組み上がる。→ **プロンプト作成の次工程(編集での尺合わせ)が省略できるようになる。**

**4. 5役合議の仕組み自体を、生成物の品質チェックに転用する**
`council.sh` は開発方針を議論するためだけに作られているが、構造としては「独立した視点で評価→まとめる」という汎用フレームである。生成された動画やプロンプト案を役に見立てて評価させる(例:「カメラ役」「色彩役」「被写体忠実度役」)使い方に転用できる。→ **プロンプトの当落判定を、単一のClaude呼び出しではなく多角的な合議で行えるようになる。**

# いま手を付けるなら

**1(生成結果の再解析・差分検出)。** 理由は単純で、新しいインフラが要らない。既存の `extract_cuts.py` と Claude 解析スキルをそのまま生成動画に対して再実行し、既存の cutsheet.json 同士を比較するだけで成立する。しかも「プロンプトを作って終わり、当たり外れは目視」という、今まさに開発者本人が毎回やっている手作業のボトルネックに直接刺さる。既存資産の転用度が最も高く、効果が本人のワークフローに即反映される。

# 捨ててよい可能性

このリストには入れていないが検討はした「文章の説明だけからカット表を仮想生成する(動画なしで企画段階のカット割りを作る)」は、今回は挙げなかった。理由は、このツールの強みが「複数キーフレームの差分からドリーとズームを判別する」といった**映像に根拠を持つ判断**にあり、動画抜きで文章から作らせると、その根拠が消えて普通のプロンプト生成チャットと変わらなくなるため。ツールの核である「解析の正確さ」を捨てて「アイデア出し」に寄る方向は、今の設計思想と逆行する。

## 理解できたこと / できなかったこと

理解できたこと: 動画の「撮り方(カメラの動き・構図・照明・色味)」と「映っている人やモノ」を分けて取り出し、撮り方だけを文章にして、別の人やモノでも同じ撮り方の映像が作れるようにする道具、というところまでは分かった。

できなかったこと: この道具を実際に使ってどのくらい時間が縮まっているのか、資料からは見えなかった。動画をドロップしてから出てくるカット表を、その後どう使って本当に新しい動画を作っているのか、その先の作業風景が書かれていない。5役の合議が「次に何を作るか」以上に、具体的に何の問題を解いているのかも掴めなかった。

## 今週の手順

1. **(上記)プロンプトを実際に生成AIに通して結果を見る** — 完了基準は上記の通り
2. **ズレが見つかった場合、`build_cutsheet.py` / `apply_subject.py` のプロンプト生成テンプレートを直す。新機能は足さない** — 完了基準: 修正後に同じ3カットで再生成し、ズレが解消したことを目視確認

- **Web UI化**: 後回し。使い手は開発者ひとりで、Macアプリのドラッグ&ドロップで用は足りている。Web UIが解決するのは「複数人からのアクセス・ブラウズ性」で、今それを必要としている人がいない
